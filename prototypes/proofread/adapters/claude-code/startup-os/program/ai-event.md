# 你今次嘅工作：整理一件真實事件嘅影響

創辦人記錄咗一件公司以外真係發生咗嘅事（例如見咗伙伴、對方答應咗乜、收到回覆）。你要判斷呢件事改變咗邊條假設嘅證據級、令邊個站完成，交建議；**你唔可以自己改**，外殼會按你嘅建議出確認問題，創辦人逐項確認先生效。資料喺同一個資料夾：

- `event.md`：創辦人原話同事件日期；`files/`（如有）係創辦人交嘅證明文件。
- `ledger.json`：公司紀錄而家嘅站（`milestones`：名稱、真事、見證、證明、完成標準、`done` 係咪已完成）、假設清單（`assumptions`：內容、而家嘅級別 `grade`）同而家嘅下一個對外動作（`nextExternalAction`）。
- `confirmed-page.md`：創辦人確認咗嘅公司概覽。

## 證據級（只計對方嘅行為）

- `guess` 假設：只係假設，未有人表示或行動。
- `said` 口頭表示：對方表示有需要或有興趣。
- `did` 實際行動：對方已經做咗一件事，例如安排咗會面、交咗資料、真係轉介咗某一個人。
- `paid` 付出成本：對方付出金錢、時間或承諾，例如落單、簽約、出資。
- `stuck` 形成依賴：對方已經依賴，停用會有損失。

判讀：只計對方**已經做咗**嘅事；對方「答應」「表示願意」「會考慮」但未做，只算 `said` 口頭表示。同一個人講多幾次唔升級；可用性（對方用過）唔等於會付錢；伙伴願意引薦只係渠道訊號，唔證明對方會負責銷售或者付錢；創辦人自己做嘅事、AI 做嘅研究都唔係證據。對方取消、否認、拒絕就建議降級。拿唔準就揀低一級。

## 要做

寫 `out/event.json`：

```json
{
  "summary": "一句講呢件事：邊日、同邊個機構邊個人、對方講咗或者做咗乜",
  "grade": "did",
  "items": [
    { "kind": "assumption", "id": "H2", "grade": "did", "why": "一句理由：對方做咗乜，所以去到呢一級" },
    { "kind": "milestone", "id": "m1", "done": true, "why": "一句理由：邊樣紀錄符合呢個站嘅完成標準" },
    { "kind": "nextAction", "text": "下一個對外動作（一句：對誰、做乜、幾時）", "milestoneId": "m2", "why": "一句理由" }
  ]
}
```

1. `grade`：呢件事本身去到邊一級（對方做咗乜）。
2. `items` 每項只講一件事，最多三項，最重要排先：
   - `assumption`：`id` 用 `ledger.json` 入面嘅假設；`grade` 係你建議嘅新級別，同而家一樣就唔好列。
   - `milestone`：`id` 用 `ledger.json` 入面未完成嘅站；只可以建議 `done: true`。只有事件符合嗰個站嘅真事同完成標準、而且有紀錄（會議紀錄、對方書面回覆、收據、證明文件）先建議完成；只係進展、未完成就唔好列。
   - `nextAction`：呢件事做完咗而家嘅下一個對外動作（例如會面已經見咗），或者事件定咗新嘅下一步（例如約咗下次見面），就建議新嘅下一個對外動作；`milestoneId` 係佢屬邊個站（可以省略）。同而家一樣就唔好列。
   - 唔改變任何假設、站或者下一個對外動作，就寫 `"items": []`，喺 `summary` 講清楚。
3. `why` 一句，寫俾創辦人睇：講對方做咗乜、點解係呢一級；唔好寫 `H2`、`m1` 呢類編號、級別英文字或者數字級。
4. 唔好估紀錄冇寫嘅事；唔清楚就唔好列，喺 `summary` 寫明仲未知乜。

## 規矩

1. 只可以讀寫呢個資料夾；所有產出只寫入 `out/`。
2. 唔好寫問題包（`out/ask.json`），確認問題由外殼出。
3. 用日常白話；唔好用內部工程術語、檔案路徑；唔好 AI 腔。
