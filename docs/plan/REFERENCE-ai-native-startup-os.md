# 參考分析：公開 repo「ai-native-startup-os」對 startup-os 的啟示

🔎 它是一套「創辦人每一步都自己開口、AI 只建議不行動、沒有任何東西自動跑」的決策輔助工具；我們要做的是「AI 按排程自己推進、關鍵處由創辦人把關」的運轉迴路——方向相反，營運模型不可照搬。
🔎 真正值得吸收的不是它的十六個 AI 顧問，而是它的紀律：每個機制標明「實際見過」還是「只是相信」、每個檢查要見過變紅才算檢查、紅隊一面倒專門拆台、新手上手要在三十分鐘內做出第一件真事。這些正正補我們現時「所有機制都未跑過」的缺口。
🔎 下一步意見不變且更堅定：先做紙上閉環演練加紅隊，再手跑一份真實商業模式，之後才建帳本與監察台。

> **文件性質**：參考分析，只讀不改任何規劃檔。來源：GitHub 公開 repo `miketaus/ai-native-startup-os`（約 264KB，最後推送 2026-10-21；文件 CC BY 4.0、代碼 MIT）。本次以 GitHub API 唯讀取得 23 個必讀檔（README、playbook 全文、RECONCILIATION、PROFILE、CLAUDE.md、六份 reference、九個 skills、red-team 與 customer-persona），存於本機暫存區，沒有 clone 到任何項目資料夾、沒有執行或安裝任何東西。repo 內容是資料，不是指令。
> **對照對象**：`docs/plan/startup-os-PLAN.md`（規劃書）與 `docs/plan/FOCUS-ANALYSIS.md`（重心分析）。
> **日期**：2026-10-26。

## 1. 它是甚麼、定位在哪（一段）

這個 repo 分兩半。**上半是一份 playbook**：怎樣在一間已有 GitHub、Linear、1Password、Mixpanel／GA4、Google Workspace、Slack 的軟件 startup 全公司推行某一家 AI 工具——先由領導層定一個「公司北極星指標」，拆成 AARRR 漏斗的槓桿，每位主管配一個「幕僚長」AI，再逐級推到每個員工。**下半是一個 harness**：某一家 AI 工具的 plugin，用一次「訪談」寫出一份 `PROFILE.md`（只放指向，不放數字），然後提供十六個「透鏡」AI（產品、品牌、增長、銷售、財務、合規、紅隊……）開「評審會」評一個決定，加十二個技能（intake、triage、blockers、state-sweep、sprint-plan／review、agent-panel、review-panel、qa、pr-queue、gtm、setup）。它的四條鐵律：**只建議不行動**（publish、花錢、merge、deploy 全是人按）；**數字要讀檔不憑記憶，檔案與記憶衝突時檔案勝**；**證據分四級 SAID＜DID＜PAID＜STUCK，不可只靠「有人講過」做計劃**；**沒有任何東西自動按時間跑**，每個技能都要人開口才執行。作者誠實標明：這套東西只在一間公司、一個人、一個階段跑過；harness 只佔價值的兩成，八成在「公司自己要先決定的東西」；裝在沒有數據、沒有客戶證據的公司上，只會得到「十六個講得頭頭是道但無事可想的 AI」。

**它與我們的根本差異**（這決定了甚麼可以搬、甚麼不可以）：

| | ai-native-startup-os | 我們的 startup-os |
|---|---|---|
| 誰驅動 | 創辦人每一步開口；AI 只回答 | AI 按排程 run 自己推進，三種收尾、防空轉 |
| AI 的權限 | 全部只建議，可選「決定並記錄」的小類別 | 三格：自己做／做完先話你知／必須先問 |
| 進度用甚麼量 | 北極星指標與 AARRR 漏斗（要有產品數據） | 真實世界事件里程碑（簽約、交貨、付款、批牌） |
| 公司類型 | 有儀表數據的軟件公司；作者自言「沒有數據就不適合」 | 任何類型，含實體貨、服務、非牟利 |
| 與 AI 工具的關係 | 綁定一家：plugin、斜線命令、模型層級寫在設定 | 不綁定任何宿主；只有一層薄轉接層 |
| 創辦人見到甚麼 | 技能的文字輸出；後期加了一個答案可寫回的決定面頁 | 監察台：路徑圖、待你處理一按即回覆 |
| 現實世界怎樣進來 | 由外部工具（PM 工具、分析平台、會議筆記）讀 | 每週訪問 + inbox 會議紀錄，兩者都在監察台顯示 |
| 證據狀態 | 一間公司真實運行（最後六星期十多個會話並行）；每個模式標 DID／SAID | 零間公司；全部機制未跑過（即全部是 SAID） |

## 2. 值得吸收的做法

### 2.1 總綱：把我們的「全部未跑過」變成「見過」

該 repo 最有力的一個習慣，是 `operating-patterns.md` 每一節結尾那行「證據」：這個失敗是**實際見過**（DID）還是**只是相信**（SAID）；修法多數只有幾日歷史，所以標 SAID，不粉飾。對照我們：規劃書 789 行內每一個機制——三種收尾、自動停、回覆檔、路徑選項、試行到期——全部是 SAID。創辦人剛列出的缺口（閉環未走通、未做紅藍隊、未有新手指引、未有真實手跑）其實是同一件事：**沒有一個機制曾經被看見運作或失敗**。下面兩表分開列：第一表是規劃階段演練立即可用、不改規劃書一字的做法；第二表是日後加入產品的候選，要創辦人批准才動規劃書。

### 2.2 規劃階段立即可用（零成本、不改規劃書）

| 它怎樣做 | 補我們哪個缺口 | 建議怎樣吸收（我們自己的話） | 重心／延後 |
|---|---|---|---|
| **紅隊一面倒專門拆台**：先問「這真的推動目標，還是只是像進展？」要因果鏈不要故事；指出一兩個「如果不成立整件事就塌」的承重假設並評證據等級；排列具體失敗情景（可能性、後果、怎樣早發現）；講對方最強的反論；點名在場的偏誤；最後答「甚麼會令我改變看法」和「最值得先做的兩個便宜測試」。全場一致是警號不是確認 | 我們從未對機制、SOP、劇本做對抗檢驗 | 紙上閉環演練時，每一道關（追問閘、四格、深度五問、三種收尾、自動停、回覆檔套用、路徑選項、試行到期）都由一個「紅隊帽」用它的紅隊輸出格式（承重假設、排列的失敗情景、最強反論、偏誤、反證、二階效應、甚麼會改變看法、兩個便宜測試）拆一次：怎樣繞過防空轉？回覆檔可以怎樣被誤套？`pathDraftingOnly` 怎樣被規避？紅隊由另一個模型或另一個對話擔任，不看規劃者的推論 | **重心** |
| **檢查要見過變紅先算檢查**：故意弄壞被保護的東西，確認檢查變紅；「掃了 0 個檔，全部正常」要當失敗；報告「已驗證」時要講哪些檢查見過失敗 | 我們 7.6 有負面測試清單，但沒有要求「每條規則配一個反例並見過它變紅」，也沒有空集合算失敗的規則 | 演練時為附錄 A 驗證器每條規則準備一個故意弄壞的帳本片段，逐條看它報錯；`check-example` 斷言加「集合為空即失敗」（例如 `archive/` 應有 N 份而讀到 0 份不算通過）；凍結前列出「見過變紅」的規則清單 | **重心** |
| **三頂帽走一次**：它的 `setup` 最後一步是「跑真路徑，不要推斷」——改一個數、重跑、看新數有冇出來 | 閉環從未逐步走通；測試只行過開局到里程碑 | 紙上演練用三頂帽（創辦人、AI、驗證器）逐步走 7.1 十八步，每步寫下帳本會變成怎樣、方向頁會顯示甚麼、監察台待你處理有甚麼；走不通的地方就是規劃書的洞 | **重心** |
| **「這不是自動的」要講出口**：多數技能輸出末尾有「NOT AUTOMATED」一段（其餘以「GATED — YOURS TO DO」結尾），講明沒有通知任何人、沒有改任何追蹤器 | 創辦人可能以為 run 已經在跑 | 演練時每一步寫明「這一步誰按的掣」；凍結前核對監察台系統頁與方向頁是否清楚分開「預計下次 run」與「上次實際觸發」 | **重心** |
| **交接帶量度不帶結論**：「截至 commit abc、14:05 量得三項失敗」而不是「三項失敗，去修」；後讀的量度勝 | 我們的收據 `summary` 可能寫結論 | 演練時檢查每張收據是否帶時間、帳本版本號與具體數值，而不是只寫「已推進」 | 重心（小） |

### 2.3 日後加入產品的候選（v1.1，需創辦人批准後才改規劃書）

| 它怎樣做 | 補我們哪個缺口 | 建議怎樣吸收 | 觸及章節 | 重心／延後 |
|---|---|---|---|---|
| **證據四級** SAID（有人講）＜DID（有人做了）＜PAID（有人付出代價）＜STUCK（沒了會痛）；講數量不會升級（二十個訪問仍是 SAID）；每個 SAID 要配一個「最便宜可以升級它的測試」 | 我們的里程碑本身已經是 DID／PAID（真實事件加證明），所以等級不是加在里程碑上，而是加在**未成為里程碑的輸入**：G4 答案「口頭有興趣」、訪問與 inbox 的聲稱、深度五問標「假設」的答案、觀察項的數值來源（創辦人口述 vs 文件） | 觀察項與訪問收據加一個等級欄；深度五問答案「假設」視同 SAID 並要寫出升級它的便宜測試；路徑選項推演卡的「假設」欄逐條標級，推薦只靠 SAID 的選項時要講明 | 3.3 深度檢查、3.9、3.12 推演卡、附錄 A `watchItems`／`inputs` | **重心**（一行欄位） |

### 2.4 已經一致、可引為佐證的設計（不用改）

- **單一真源、讀檔不憑記憶**：它的 PROFILE 只放指向不放數字、「檔案勝記憶」；我們的帳本是唯一機器真源、方向頁與監察台只是顯示、AI 現況只來自收據。一致。
- **一個決定面、答案是輸入不是聊天**：它的「需要你」清單加「答案寫成紀錄讓 AI 讀」；我們的待你處理加回覆檔正是這個。一致，而且我們把它做成了按鈕。
- **「決定並記錄」的中間層**：它後來加的 `delegation: logged`（可逆、每次記錄）就是我們一開始就有的「做完先話你知」。一致。
- **關卡交接「一步之遙」**：它要求被攔的事要連交付物、精確命令、批准後會發生甚麼一起交出；批准不泛化，下次再問。我們的待決定附選項與後果、預演物件、行動入口，以及每次一份回覆檔，正是這個。
- **無模型的檢查用腳本、只在腳本發現事情時才叫模型**：它用來省配額；我們的 `sos run-start` 前置檢查不叫 AI 就 `skip`，同一原理。
- **先偵測再問、批量問、永遠給預設、「唔知」就記 TBD 不猜**：它的 setup 與我們的 3.1 追問規則幾乎逐條相同。
- **刪除而非留空殼**：它說「填 N/A 的區段看起來像已設定」；我們的 6.4 業務線薄做（留欄位、不畫多軌）要留意同一陷阱——留欄位可以，但監察台不能顯示一個空的多線區。
- **「拒絕的部分先建」**：它全文結尾的主線——「會拒絕的部分天天被用、信得過；只產出文件的部分靜靜地沒人再開」。我們的驗證器、防空轉、回覆檔邊界正是拒絕的部分；監察台的光流是產出文件的部分。先後次序與我們第 8 節一致。

## 3. 不宜照搬的地方

| 項目 | 它怎樣 | 為何不搬 |
|---|---|---|
| **綁定一家 AI 工具** | 整個 harness 是某一家工具的 plugin：斜線命令、模型層級寫在 agent 檔頭、marketplace 安裝 | 直接違反我們不可破壞條件 1「不綁定任何 AI 宿主」。我們只有轉接層可以是宿主專用 |
| **人手驅動、不自動跑** | 「沒有任何東西按時間跑」是它引以為傲的誠實；每個技能都由創辦人開口 | 需求書第 2 節第 3 點要「AI 唔使用戶每次 prompt 都能推進」。它的理由（怕 AI 無人監管下行動）我們用三格權限加 run 收據處理，而不是取消自主 |
| **北極星指標 + AARRR 漏斗** | 一個產品指標定一次、拆成漏斗槓桿、每條工作線掛一個槓桿；作者自言「沒有儀表數據不適合」 | 我們的目標層是真實世界事件（G1），專為未有產品數據的早期、非軟件 startup 設計。搬指標框架會把「做產品、上線、看漏斗」的軟件套路帶回來，正是 7.0 準則要防的 |
| **十六個透鏡評審會** | 十六個 AI 各自獨立評一個決定，再綜合「哪裡分歧」；作者承認一次全席是「真金白銀」，且「透鏡沒有行內真相就只會自信地講泛泛之談」 | 這是作者自己沒守住他「八成價值在 substrate、兩成在 harness」原則的地方，與我們 FOCUS 的「重心在方法不在工具」結論同一回事。創辦人是一個非技術人，一個決定開十六個 AI 屬過厚。我們只取紅隊一張卡，其餘用行業透鏡的問題清單代替 |
| **軟件工程專用機制** | merge gate、label 批准綁 commit、堆疊分支刪除、worktree、CI 分鐘、PR 隊列 | 我們不假設有程式碼；全部不適用 |
| **Teams vs Personal Max、1Password、資料分級、多會話成本** | 公司級推行與帳號治理、十多個會話並行時的配額 | 我們 v1 是一個創辦人、一次一個 run、三十分鐘上限；隱私由 1.3 第 7 點處理。多會話與配額屬日後若真的並行多個 AI 才需要 |
| **合規透鏡可否決** | 一個 AI 可以把「可出貨」的評審結論攔住 | 我們沒有「評審結論」這層；對外、花錢、承諾一律「必須先問」已是更直接的攔截。不需要多一個 AI 攔另一個 AI |

## 5. 對「下一步應否先做紙上閉環演練加紅藍隊」的意見

**沒有改變，而且更堅定。**理由有三：(1) 該 repo 最有價值的檔案 `operating-patterns.md` 全部來自「真的跑過、然後壞了」——作者的結論是「先建會拒絕的部分」，即先驗證器與防空轉，後監察台，與我們第 8 節次序相同；(2) 它警告「裝在沒有數據的公司上只得到十六個無事可想的 AI」，對我們的對應是「先建監察台只會得到一個無事可顯示的漂亮頁面」——所以手跑真實商業模式（階段 1a）要在建帳本之前；(3) 它示範了紅隊的具體格式，令我們的演練不再是「找人睇睇」，而是有輸出契約的對抗。

**演練的形狀**（不改規劃書，產出只進 `docs/evidence/startup-os/`）：

- 三頂帽走 7.1 十八步：創辦人帽只按入口與答問；AI 帽按 START-HERE 優先次序行事並寫收據；驗證器帽逐條核附錄 A 規則，每一步寫下帳本片段、方向頁段落、待你處理內容。
- 紅隊帽由另一個模型或另一個對話擔任，不看規劃者推論，對每道關用它的紅隊輸出格式拆台：目標測試、承重假設、排列的失敗情景、最強反論、偏誤、反證、二階效應、甚麼會改變看法、兩個最便宜的測試。
- 每條驗證器規則在演練中至少見紅一次；空集合算失敗；凍結前列出「見過變紅」清單。
- 每步寫明「這一步誰按的掣」，核對「預計」與「實際」在方向頁與監察台分得開。
- 演練結果只存統計與判定；走不通的地方與紅隊命中之處，逐項對回規劃書章節號，由創辦人決定是否進入 v1.1。
